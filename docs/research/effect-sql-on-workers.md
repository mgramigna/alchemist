# Effect v4 SQL on Cloudflare Workers: D1 vs Postgres over Hyperdrive

## Bottom line

- **D1 has a direct Effect 4.0.6 Workers binding client, including atomic batches, but no interactive `SqlClient.withTransaction`.** The latter dies with a defect. This also prevents using Effect's shared transactional migrator unchanged; Wrangler SQL migrations are available. Whether an operation can be expressed as a fixed batch is a material design constraint. [D1 client][d1-source], [shared migrator][migrator], [Wrangler migrations][d1-migrations].
- **Postgres has interactive transactions, savepoints, streaming and migrations in Effect 4.0.6, but its Hyperdrive compatibility is not established here.** The published driver is a native wire-protocol implementation using Node TCP/TLS, not a wrapper around `pg`. Cloudflare documents `pg` and Postgres.js support; that is not evidence that Effect's different driver works end to end. [Pg client][pg-source], [Pg transport][pg-connection], [Cloudflare driver guidance][cf-pg].
- **Both paths can cost $0 at intermittent small-group usage.** D1 Free includes 5 million rows read/day, 100,000 written/day and 5 GB/account, with a separate 500 MB/database cap. Hyperdrive Free includes 100,000 statements/day; Neon Free currently includes 100 CU-hours/month/project and 1 GB/project. Workers Paid starts at $5/month and includes Hyperdrive without a separate surcharge; Neon remains a separate bill. [D1 pricing][d1-pricing], [D1 limits][d1-limits], [Hyperdrive pricing][hd-pricing], [Neon pricing][neon-pricing], [Workers pricing][workers-pricing].
- **Hyperdrive caching affects correctness:** enabled by default, with no write-triggered invalidation. Editing and authentication reads need a deliberate freshness policy. Exact application latency, deployed bundle size, and native Effect-driver compatibility remain unmeasured. This research records trade-offs and does not select a database. [Query caching][hd-cache].

## Evidence and version boundary

Researched **2026-10-25** for [issue #3](https://github.com/mgramigna/alchemist/issues/3), against the repository's exact catalog version, **4.0.6**. Pricing is USD at the observation date, before tax; quotas and prices can change.

I downloaded and inspected the published npm tarballs and manifests for [`effect@4.0.6`](https://registry.npmjs.org/effect/4.0.6), [`@effect/sql-d1@4.0.6`](https://registry.npmjs.org/@effect%2fsql-d1/4.0.6) and [`@effect/sql-pg@4.0.6`](https://registry.npmjs.org/@effect%2fsql-pg/4.0.6). The two adapter client source files match the canonical repository's `effect@4.0.6` tag, commit `3b28bf686bf26e9700edd39c025aff2744dc5303`, byte for byte. Both adapters declare `effect: ^4.0.6` as a peer; the project can pin matching adapter versions through its catalog. SQL abstractions are under `effect/sql/*` in this release. See the published manifests linked above and the [release source][pg-source].

The requested [`Effect-TS/effect-smol`](https://github.com/Effect-TS/effect-smol) repository is archived and says v4 moved to `Effect-TS/effect`. I also inspected its archived [Postgres client](https://github.com/Effect-TS/effect-smol/blob/3a1128c7684e04d34d9f541f77adaac38a513056/packages/sql/pg/src/PgClient.ts) and [D1 client](https://github.com/Effect-TS/effect-smol/blob/3a1128c7684e04d34d9f541f77adaac38a513056/packages/sql/d1/src/D1Client.ts). Its Postgres client imports `pg` and `pg-cursor`; **that historical implementation is not the published 4.0.6 implementation**. This distinction makes older v4 examples, as well as v3 docs, unsafe evidence for the pinned driver.

## Effect client support and maturity

### D1

`@effect/sql-d1/D1Client` adapts a `D1Database` supplied as `{ db: env.DB }`, exposing both `D1Client` and generic `SqlClient` services. It uses SQLite SQL compilation and the binding's prepared statements, with configurable preparation caching and query/result name transforms. The Workers types import is type-only; this path does not introduce a Node database socket driver. The module labels itself `@stability unstable`. These are source-level support facts, not a claim of production validation for Alchemist. [D1 client][d1-source].

`D1Client.batch([...statements])` compiles a fixed collection of Effect statements and executes the binding's atomic batch, returning ordered row results. This can cover an import or replacement operation whose IDs and statements are known in advance. It cannot express arbitrary application code that reads a result, branches, and then writes within the same transaction; the implementation explicitly bypasses `SqlClient` transaction acquisition. `withTransaction` acquires `Effect.die("transactions are not supported in D1")`, rather than returning a recoverable `SqlError`. Streaming and `updateValues` are also unsupported. [D1 client][d1-source].

The published package contains `D1Client` and its index, with no D1-specific migrator. The shared `effect/sql/Migrator` wraps SQLite migrations in `sql.withTransaction`; using it unchanged therefore reaches the unsupported transaction path. This is an inference from both implementations, not an executed migration test. Wrangler supplies numbered `.sql` migrations, an applied-migration ledger (`d1_migrations`), and create/list/apply commands. A deployment migration step is available independently of Effect's migrator. [Package contents](https://unpkg.com/@effect/sql-d1@4.0.6/src/), [shared migrator][migrator], [Wrangler migrations][d1-migrations].

### Postgres

`@effect/sql-pg/PgClient` 4.0.6 implements the PostgreSQL wire protocol itself. Its published manifest has no runtime dependency on `pg`, Postgres.js or `pg-cursor`; its connection implementation imports `node:net`, `node:tls`, `node:crypto`, buffers and streams. It offers a scoped pool (`make`/`layer`), a single-connection client (`makeClient`), prepared-statement configuration, reserved transaction connections, savepoint release, streaming, JSON and listen/notify helpers. It and the SQL migrator are marked unstable. [Published manifest](https://registry.npmjs.org/@effect%2fsql-pg/4.0.6), [Pg client][pg-source], [transport][pg-connection].

Workers now documents outbound Node TCP/TLS support. Node compatibility is enabled by default at compatibility dates from 2026-08-04; earlier dates require `nodejs_compat`. This removes an obvious missing-module objection, but is **not** a confirmation of Effect's SSL negotiation, authentication, cancellation or prepared-statement behavior through Hyperdrive. Cloudflare explicitly documents `pg` and Postgres.js and warns that other drivers' named prepared statements may perform worse or be unsupported. Effect offers `prepare: false`, a possible integration setting to evaluate rather than a verified fix. [Workers net](https://developers.cloudflare.com/workers/runtime-apis/nodejs/net/), [Workers TLS](https://developers.cloudflare.com/workers/runtime-apis/nodejs/tls/), [driver guidance][cf-pg], [Hyperdrive pooling][hd-pool], [Pg configuration][pg-source].

`PgMigrator` reuses the shared migrator, which records migration IDs and runs pending migrations transactionally, with a PostgreSQL table lock. Loaders include `fromRecord` and `fromFileSystem`. Schema dumps invoke `pg_dump` and use process/filesystem facilities; `PgMigrator` itself imports Node filesystem/process-related modules. A Node deployment/CI migration job connecting directly to the origin is a concrete available route. Importing the migration tool into a request Worker adds irrelevant runtime dependencies, and is not validated here. [Shared migrator][migrator], [Pg migrator][pg-migrator].

## Setup, local development and operation

### D1 binding path

Create a D1 database, bind it to the Worker, and construct the Effect layer from that binding. Wrangler local development uses a local database with persisted state; migration application distinguishes `--local` from `--remote`. This permits offline SQL development without provisioning a local Postgres server. Local data and remote data are separate. [D1 local development](https://developers.cloudflare.com/d1/best-practices/local-development/), [migrations][d1-migrations], [Effect binding constructor][d1-source].

D1 is SQLite-based. A database processes queries serially, so throughput depends on query duration; batching reduces binding round trips but does not create independently parallel writes. Data location and optional session-based read replication affect latency; a binding is not a promise that all reads and writes execute at the caller's edge. Read replication requires the Sessions API; using `env.DB` directly continues to query the primary. The Effect adapter has no dedicated session/bookmark API, and a session-based integration was not confirmed. No comparative latency benchmark was run. [D1 limits][d1-limits], [data location](https://developers.cloudflare.com/d1/configuration/data-location/), [read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/).

### Neon/Postgres through Hyperdrive

Provision a Neon project, database and role; use its **direct, unpooled** Postgres connection string to create the Hyperdrive configuration. Bind that configuration to the Worker and pass its runtime `connectionString` to the SQL client. Cloudflare's Neon guide explicitly turns off Neon's pooling for this path. Hyperdrive supplies pooling, not database storage; the same arrangement can front another supported managed or self-hosted PostgreSQL origin. [Neon setup][hd-neon], [supported databases][hd-features].

Hyperdrive pools in transaction mode: one backend is retained throughout a transaction and returned afterward. Session `SET` state does not persist across independent transactions. `LISTEN`/`NOTIFY`, advisory locks and SQL-level `PREPARE`/`EXECUTE` management are unsupported, even though some are available on Effect's client interface. Wire-protocol prepared statements are a separate feature, with the driver caveat above. These limitations do not establish a CRUD blocker, but prohibit assuming every Postgres feature is available. [Pooling][hd-pool], [supported features][hd-features].

Cloudflare's driver example creates a client within each request because Hyperdrive maintains origin connections. For Effect, a request-scoped client/pool with deterministic scope closure is an implementation implication, not a tested recipe. The default Effect pool permits 10 connections; Workers permits six simultaneous outgoing connections per request, so pool sizing must account for other request I/O. A shared application runtime must not reuse request-owned sockets across invocations. [Cloudflare example][cf-pg], [Effect pool][pg-pool], [Workers limits][workers-limits], [request I/O constraints](https://developers.cloudflare.com/workers/observability/errors/#cannot-perform-io-on-behalf-of-a-different-request).

Local `wrangler dev` uses `localConnectionString` or `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_<BINDING_NAME>` to reach local Postgres or a remote development database directly. **Local mode bypasses Hyperdrive pooling and caching**, so successful local queries do not prove deployed compatibility. Remote development uses the configured Hyperdrive origin. [Local development][hd-local].

Pooling avoids repeated origin connection setup; optional read caching can avoid origin round trips. Uncached queries and transaction statements still travel to the Postgres region. Neon wakes an idle compute on connection, generally adding a few hundred milliseconds and cold-buffer effects. No deployment-specific latency comparison is confirmed. Hyperdrive's persistent connections do not justify assuming Neon is always awake: Neon can close truly idle connections on suspension, while repeated connection attempts reset its inactivity timer. Actual idle compute usage with this integration remains unmeasured. [Pooling][hd-pool], [Neon lifecycle](https://neon.com/docs/introduction/compute-lifecycle), [Neon compute management](https://neon.com/docs/manage/endpoints).

Hyperdrive read caching defaults to 60 seconds of freshness plus 15 seconds of stale-while-revalidate and does not invalidate on writes. A matching read can therefore lag a completed edit. Cloudflare documents cache-disabled configurations for reads requiring freshness, including authentication. The editor, owner authorization and immediate export semantics need an explicit policy if Hyperdrive is used. [Caching][hd-cache].

Alchemy documents provisioning [D1](https://alchemy.run/cloudflare/data/d1/) and lists [Hyperdrive as the Workers path to external Postgres](https://alchemy.run/sql/databases/). That establishes infrastructure options within the standing deployment tool; this research does not confirm the project's future Alchemy version or a complete Effect-native wiring recipe.

## Small-group cost model

- **D1 Free:** 5 million rows read/day, 100,000 rows written/day, 5 GB total storage. Reads count scanned rows, not just rows returned, so indexes affect consumption. Free limits stop operations rather than seamlessly becoming a paid overage. Separately, each Free database is limited to 500 MB. [Pricing][d1-pricing], [limits][d1-limits].
- **D1 on Workers Paid:** first 25 billion reads/month, 50 million writes/month and 5 GB included; additional reads $0.001/million, writes $1/million and storage $0.75/GB-month. The account's Workers subscription starts at $5/month. D1 has no active-hour compute bill. [D1 pricing][d1-pricing], [Workers pricing][workers-pricing].
- **Hyperdrive:** included on Free with 100,000 database statements/day, and unlimited statements on Workers Paid without a separate Hyperdrive charge. DDL and writes count as statements too. Free quota exhaustion returns errors until the daily reset. This is distinct from D1's rows-based billing. [Hyperdrive pricing][hd-pricing].
- **Neon Free:** $0, 100 CU-hours/month/project, 1 GB storage/project, 5 GB public transfer/project, scale to zero after five inactive minutes, and up to six hours/1 GB of change history for instant restore. At 0.25 CU, 100 CU-hours is 400 active hours, not unlimited always-on compute. Exceeding compute/transfer quotas suspends compute until reset or upgrade; storage limits block growth. [Pricing][neon-pricing], [Free plan quotas](https://github.com/neondatabase/website/blob/main/content/faqs/free-plan-limits-and-quotas.md).
- **Neon Launch if Free is insufficient:** $0.106/CU-hour plus $0.35/GB-month of database storage, with no monthly minimum. Restore-history storage and optional resources can add charges. The pricing page's “typical spend” is an illustration, not a minimum subscription. [Pricing][neon-pricing], [Neon's pricing explanation](https://neon.com/blog/new-usage-based-pricing).

For an illustrative workload of 10,000 statements/day, no more than 100,000 scanned rows/day and 1,000 written rows/day, a database below 500 MB, and 20 active Neon CU-hours/month, either persistence path fits the listed free allowances. This is arithmetic under explicit assumptions, not a forecast based solely on user count. If Workers Paid is already needed for CPU or other platform limits, its $5 base is common to both paths; database charges may still be $0. A continuously active 0.25-CU Neon compute uses about 180 CU-hours in a 30-day month, exceeding Free. On Launch, that compute alone is about $19.08/month, plus storage and other usage. See [Neon rates][neon-pricing] and [Workers rates][workers-pricing].

## Blockers, known reports and unconfirmed facts

- **D1 operation shape and limits:** interactive transactions, streams and `updateValues` are missing from the Effect adapter. D1 additionally caps bound parameters at 100/query, SQL at 100 KB and a row/string/BLOB at 2 MB. Large imports must respect per-statement limits even inside batches; a batch counts once against D1's queries-per-invocation limit. Paid databases cap at 10 GB. These are specific constraints, not evidence that small-group storage is insufficient. [Client][d1-source], [limits][d1-limits].
- **Postgres known report confirmed in source:** open [Effect #9932](https://github.com/Effect-TS/effect/issues/9932) reports refusal above 32,767 bound parameters. The 4.0.6 `PgProtocol` still checks `count > 0x7fff`; it affects very large parameterized statements, not ordinary single-character edits. [Pinned protocol source][pg-protocol].
- **Other open reports:** [#9895](https://github.com/Effect-TS/effect/issues/9895) reports a hanging listen-scope finalizer on a dead connection in 4.0.6; Hyperdrive already excludes LISTEN. [#9875](https://github.com/Effect-TS/effect/issues/9875) reports generic Effect pool fairness issues in 4.0.6. These are maintainer-repository reports, not independently reproduced bugs in Alchemist. No open issue matched the bounded `sql-pg hyperdrive` search; that is not proof of compatibility or absence of bugs.
- **Bundle size:** published npm unpacked sizes are 53,470,246 bytes for `effect`, 251,810 for D1 and 969,410 for Postgres. Those include source, declarations/maps and other files; they are **not deployed bundle measurements**. Both adapters declare `sideEffects: []`; actual size depends on imports and bundling. Current Workers docs list a 64 MiB uncompressed limit, no compressed-size limit, and a one-second startup limit. A future `wrangler deploy --dry-run --outdir …` can measure the real app; no such bundle or deployment was produced here. [npm manifests above], [Workers limits][workers-limits].
- **Remaining unknowns:** actual Effect 4.0.6 Postgres transport behavior through deployed Hyperdrive; whether disabling named preparation is necessary/sufficient; deployed bundle/startup/CPU cost; production query latency; Neon compute consumption under the resulting pool lifecycle. D1 binding support is explicit in its adapter, but no live D1 migration/import run was performed. No project database decision or up-front application spike is implied by these gaps.
